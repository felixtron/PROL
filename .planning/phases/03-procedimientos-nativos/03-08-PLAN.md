**Lo que cambia esta fase en la base**, y es lo que la diferencia del despliegue de
la fase 2 (que no tocaba Prisma):
- `CREATE TYPE "ManualDocumentKind"` y `CREATE TYPE "CompanyDocumentStatus"`.
- `manual_documents`: `+ kind`, `+ content_html`, `+ template_version`.
- `company_documents`: `+ kind`, `+ content_html`, `+ name_override`, `+ status`,
  `+ source_template_version`, `+ published_at`, `+ published_by` (con su FK).
- `company_documents`: `file_key`, `file_name`, `file_size`, `mime_type` pasan a
  **nullable** (`DROP NOT NULL`).
Todo aditivo salvo los cuatro `DROP NOT NULL`, que no pierden datos ni requieren
backfill. Los dos enums son **nuevos**, así que es `CREATE TYPE` normal y no aplica
el caveat de `ALTER TYPE ... ADD VALUE` fuera de transacción.

**Backfill del invariante** (mismo SQL que ejecutó el plan 03-01 en local; allí fue
un no-op comprobado, aquí hay que comprobarlo, no suponerlo):
```sql
UPDATE company_documents c
SET status = 'OBSOLETO'
WHERE c.status = 'VIGENTE'
  AND EXISTS (
    SELECT 1 FROM company_documents c2
    WHERE c2.document_id = c.document_id
      AND c2.company_id  = c.company_id
      AND c2.version     > c.version
  );
```
`status` entra con `DEFAULT 'VIGENTE'`, así que **toda fila preexistente queda
vigente**. Si alguna empresa de producción tuviera dos versiones del mismo
documento, quedarían dos vigentes y el arreglo de OPS-05 devolvería dos filas donde
debería devolver una. Contar antes:
```sql
select count(*) from company_documents;
```

- *El riesgo real es el `db push`*, y no por lo que hace —todo aditivo salvo cuatro

  reiniciara antes de aplicar el esquema, arrancaría contra columnas que no

- *Riesgo heredado*: entra también el arreglo del 401, que cambia el código de
  respuesta de ocho rutas de 403 a 401 cuando no hay sesión. Es lo correcto y ya
  está verificado en local con las tres sesiones, pero es un cambio de
  comportamiento observable.

1. Retaggear `localhost/prol-web:55c020d` como `latest` y reiniciar. Las columnas
   nuevas se quedan en la base sin molestar: el código anterior no las lee. Es el
   rollback realista y basta para todo salvo una catástrofe del push.
2. Lo anterior más restaurar el dump `pre_fase3`, si el `db push` dejara la base en
