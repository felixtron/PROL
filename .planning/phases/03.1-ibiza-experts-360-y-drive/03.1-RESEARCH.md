## Summary

Esta fase es un refactor de aplicación sobre un dominio ya construido, no una integración nueva: no hace falta ninguna librería, SDK o servicio externo. Todo el trabajo es (a) plumbing de datos —dos columnas nuevas y aditivas—, (b) una relajación puntual de una validación, y (c) una capa de presentación (agrupar nav, mostrar un enlace externo validado en vez de un botón de subida).

El hallazgo más importante de "leer el código real primero" es que **el circuito de cumplimiento ya está escrito para tolerar evidencia sin archivo**: `canSubmitEvidence`, `activityState`, `completeActivityAndScheduleNext`, la cola de revisión (`evidence-queue.tsx`), la ficha de revisión (`evidence-detail.tsx`) y el panel del líder (`dashboard/company/evidence/page.tsx`) ya renderizan `fileName` como opcional (`evidence.fileName ? <a>...</a> : null`) porque `RISK_MATRIX` y `EVALUATION_LINK` nunca tuvieron archivo. Esto significa que el criterio 7 (DRV-04) tiene un blast radius mucho más pequeño de lo que el nombre de la fase sugiere: un solo `if` que rechaza, un botón que cambia de "Subir evidencia" a "Marcar como cumplido", y una etiqueta de texto. Nada del backend de cumplimiento, la agenda, el cron o la bitácora necesita cambiar.

La segunda mitad —agrupar la navegación— es pura UI: los cuatro/tres destinos que hay que agrupar (Manuales, Proyectos, Evidencias, Agenda) **ya son rutas hermanas independientes** (`/tenant-admin/manuals`, `/tenant-admin/projects`, etc.); "agrupar bajo un menú" no mueve ni una URL, sólo cambia cómo se renderiza la lista de navegación. `sidebar-shell.tsx` (usado por tenant-admin, admin y professor) renderiza su lista de navegación desde un único bloque JSX compartido entre escritorio y el drawer móvil, así que un solo componente de "grupo colapsable" nuevo resuelve escritorio+móvil para tenant-admin y professor a la vez. El panel del cliente (`app/dashboard/layout.tsx`) tiene su propio par de componentes (`sidebar-nav.tsx` para escritorio, `mobile-nav.tsx` para el tab-bar+hoja "Más" del móvil) que **no comparten código con `sidebar-shell.tsx`** — recomendación abajo: no migrar todo el layout del cliente, pero sí extraer el renderizador de item-de-grupo a un módulo compartido para no triplicar la lógica de acordeón.

**Primary recommendation:** No añadir un valor nuevo a `EvidenceRequirementKind`. Reutilizar `FILE` y quitarle la exigencia de archivo — es el mismo código, exactamente el mismo blast radius de UI (el branch de `evidence-block.tsx` hay que reescribirlo de todos modos, tenga el kind el nombre que tenga), y evita tocar `packages/db/prisma/schema.prisma` en una zona de enums justo cuando otra sesión lo tiene con cambios reales sin commitear.

## Architecture Patterns

### 1. Criterio 7 — blast radius completo de "un requisito se cumple sin archivo"

**El punto de apertura, confirmado línea por línea (`apps/web/lib/actions/evidence.ts:120-129`):**

```typescript
const kind = activity.requirement.kind;
if (kind === "FILE" && !input.file) {
  return { success: false, error: "Adjunta el archivo de la evidencia" };
}
if (kind === "RISK_MATRIX" && !input.riskAssessmentId) {
  return { success: false, error: "Falta la matriz que sustenta la evidencia" };
}
if (kind === "EVALUATION_LINK" && !input.evaluationSubmissionId) {
  return { success: false, error: "Elige la entrega de evaluación a asociar" };
}
```

Cambio mínimo: quitar la rama `FILE` (o convertirla en no-op), dejando que `submitEvidence({ activityId, notes })` sin `file` cree la fila con `fileKey: null, fileName: null, fileSize: null, mimeType: null` — exactamente el mismo `data` object que ya escribe hoy cuando `input.file` es `undefined` (línea 163-166: `fileKey: input.file?.fileKey ?? null`, etc.). **No hace falta tocar el `create` en absoluto**, sólo el guard.

**Inventario exhaustivo de todo lo que toca `EvidenceRequirementKind` o asume archivo, con veredicto:**

**Confirmación explícita del alcance de la pregunta "¿la agenda se ve afectada?":** no. La agenda, el cron y la bitácora (`EvidenceReview`) son 100% independientes de si la evidencia tiene archivo. Esto es justo lo que la Decisión 1 de CONTEXT pedía verificar, y el código lo confirma sin ambigüedad.

### Decisión de diseño: ¿nuevo valor de enum o reutilizar `FILE`?

**Argumento a favor de un valor nuevo (`DRIVE_FOLDER` o similar):** mayor autodocumentación — el nombre "FILE" deja de significar literalmente "archivo en PROL" y pasa a significar "archivo, y vive en Drive", lo cual es una redefinición silenciosa de una constante existente.

**Argumento en contra, y por qué pesa más:**

1. **El costo de UI es idéntico con o sin el valor nuevo.** `evidence-block.tsx` necesita una rama nueva de todos modos (ni `RISK_MATRIX` ni `EVALUATION_LINK` cubren "mostrar enlace de Drive + botón marcar-cumplido"); llamarla `case "FILE"` o `case "DRIVE_FOLDER"` no cambia una sola línea de esa rama.
2. **No hay coexistencia que preservar.** El alcance de la fase es "todo el expediente de archivos sale de PROL" — no hay un escenario donde algún requisito siga pidiendo "sube el archivo a PROL de verdad" en paralelo a otro que use Drive. Si no hay dos comportamientos que distinguir, un enum con dos valores para la misma cosa no aporta seguridad de tipos, sólo un sinónimo.
3. **Coste de infraestructura no compensado.** Añadir un valor a un enum de Postgres (`EvidenceRequirementKind` es un enum nativo, `datasource db { provider = "postgresql" }`, confirmado en el schema) puede requerir `ALTER TYPE ... ADD VALUE`, que en Postgres ≤ 11 debía correr fuera de transacción, y en Postgres 12+ (este proyecto corre `pgvector/pgvector:pg16` en dev, confirmado en `docker-compose.yml:6`) puede ejecutarse dentro de una transacción pero el valor nuevo no puede *usarse* (leerse/escribirse) en esa misma transacción. Con `db push` (no hay carpeta de migraciones) esto es manejable, pero es una superficie de riesgo real que un cambio de nombre de campo no tiene.
4. **El archivo que hay que tocar para cualquiera de las dos opciones está ahora mismo mid-edit por otra sesión** (`packages/db/prisma/schema.prisma`, ver Common Pitfalls). Un cambio de enum toca la sección de enums (línea ~406) Y el modelo `EvidenceRequirement`/`Evidence` en teoría no, pero añade riesgo de tocar una zona compartida sin necesidad, cuando la alternativa (relabeling) no toca el schema en absoluto para este punto.
5. **Precedente del propio repo:** `ManualDocumentKind` (`FILE | PROCEDIMIENTO | REGISTRO`) es un enum *distinto y no relacionado* que ya vive en el mismo schema con un valor también llamado `FILE` (para plantillas, no evidencias) — confirmando que el repo ya tolera que "FILE" signifique "el contenido vive fuera de la BD, en un storage de archivos" sin que eso implique "vive en el disco de PROL". Ese precedente hace que reetiquetar `EvidenceRequirementKind.FILE` como "vive en Drive" sea coherente con cómo el repo ya usa la palabra "FILE" en otro enum del mismo dominio.

**Recomendación: NO añadir un valor de enum. Reutilizar `FILE`, relajar el guard, y cambiar sólo las etiquetas humanas** (`KIND_LABEL.FILE` en `section-requirements-editor.tsx`, y opcionalmente la descripción de `/dashboard/manuals/page.tsx`). Si el planificador prefiere de todos modos un valor nuevo, la superficie exacta a modificar es: enum en `schema.prisma:406-410`, el `switch`/`if` en `evidence.ts:120-129`, y el `union` de tipos en `evidence-block.tsx:275-291` (añadir un tercer `: requirement.kind === "DRIVE_FOLDER" ? ... :` antes del `else` genérico) — nada más, porque ningún otro sitio de la tabla de arriba mira `kind`.

### 2. Blast radius de navegación — qué layouts tocar y cuáles no

**Los tres paneles que NAV-02 pide (administrador, consultor, cliente) mapean exactamente a:**

| Panel | Layout | Items del módulo hoy | Líneas |
|---|---|---|---|
| Administrador | `apps/web/app/tenant-admin/layout.tsx` | Manuales, Proyectos, Evidencias, Agenda | 58-68 (bloque `showDocuments ? [...] : []`) |
| Consultor | `apps/web/app/professor/layout.tsx` | Proyectos, Evidencias, Agenda (sin Manuales — "la autoría de los manuales vive en el panel del administrador", comentario explícito en el propio archivo) | 59-67 |
| Cliente | `apps/web/app/dashboard/layout.tsx` | Manuales, Documentos, Agenda | 95-113 |

**El panel super-admin (`apps/web/app/admin/layout.tsx`) NO tiene ningún item del módulo** (Tenants, Usuarios, Ingresos, Profesores, Configuración, Docs — confirmado leyendo el archivo completo, 59 líneas). No forma parte de NAV-02 y no debe tocarse.

**Forma actual de `SidebarNavItem`** (`apps/web/components/nav-icons.ts:46-52`):

```typescript
export interface SidebarNavItem {
  href: string;
  label: string;
  icon: SidebarIcon;
}
```

Plano, sin `children`. Necesita una extensión opcional:

```typescript
export interface SidebarNavItem {
  href: string;
  label: string;
  icon: SidebarIcon;
  children?: SidebarNavItem[];
}
```

Un item con `children` no navega por sí mismo (no tiene página propia — el "menú" es un concepto puramente de UI, ninguna de las 4 rutas hijas cambia de URL). El render debe distinguir: item sin `children` → `<Link>` normal (comportamiento actual, sin tocar); item con `children` → cabecera colapsable + lista de `<Link>` hijos con la misma indentación/estilo que ya usan los items planos.

**`resolveActiveHref` (`apps/web/components/nav-active.ts`, 20 líneas) hoy sólo sabe resolver "cuál de esta lista plana de hrefs es el actual", con la regla de "el match más largo gana"** (para que `/tenant-admin` no se ilumine cuando la ruta real es `/tenant-admin/users`). Esta función **no necesita cambiar** para decidir qué hijo está activo (se le sigue pasando la lista plana de hrefs, aplanando el árbol antes de llamarla). Lo que sí hace falta añadir es lógica nueva, no dentro de `resolveActiveHref` sino en el componente que renderiza el grupo: "¿el `activeHref` resuelto pertenece a alguno de mis `children`? → entonces este grupo debe pintarse expandido/resaltado". Esto es una función pura nueva y pequeña (p. ej. `groupContainsHref(group, activeHref)`), no una reescritura de la existente.

**Persistencia de expandir/colapsar:** el repo **no tiene ningún store de estado de cliente** (confirmado: cero resultados de `localStorage`, `sessionStorage`, `zustand`, o un `create(set...)` en todo `apps/web`). Recomendación: no inventar persistencia. Derivar el estado "abierto" de `pathname` en cada render (`useMemo` sobre si `pathname` cae dentro de los hrefs del grupo), igual que ya hace `resolveActiveHref`. Esto es correcto en recarga completa, navegación con botones atrás/adelante, y enlaces directos — y punto a favor: `SidebarShell`/`SidebarNav` **no se desmontan entre navegaciones dentro del mismo layout** (Next.js App Router mantiene montado el árbol del layout compartido; sólo re-renderiza `{children}`), así que si además se quiere permitir que el usuario abra manualmente un grupo que no contiene la ruta activa, un `useState<Set<string>>` local sobrevive la navegación sin ningún store — no hace falta `localStorage` para eso tampoco.

**Precedente visual de acordeón ya existente en el repo** (`apps/web/components/knowledge-base.tsx:590-630`): botón con `aria-expanded`, `ChevronDown` que rota 180° cuando `open`, contenido condicional debajo. Seguir exactamente este patrón para el grupo de nav mantiene consistencia visual sin inventar un componente nuevo de cero.

**Mobile:** `sidebar-shell.tsx` renderiza el mismo bloque `sidebarContent` tanto en el `<aside>` de escritorio como dentro del drawer móvil (líneas 54-89, reutilizado en 97 y 121) — cualquier componente de grupo que se añada ahí funciona en ambas superficies automáticamente, sin trabajo extra. **Esto no aplica al panel del cliente**, que tiene dos componentes de nav completamente separados y sin código compartido con `sidebar-shell.tsx`:
- `apps/web/app/dashboard/sidebar-nav.tsx` (lista de escritorio, 45 líneas) — misma estructura de link que `sidebar-shell.tsx` pero archivo independiente.
- `apps/web/app/dashboard/mobile-nav.tsx` (176 líneas) — un tab-bar de 4 destinos fijos + una hoja modal "Más" que lista todo lo que no está en esos 4 (Manuales/Documentos/Agenda del módulo ya caen ahí, en `overflowItems`, hoy como una lista plana).

**Recomendación sobre unificar o no** (pregunta explícita de CONTEXT y de la investigación): **no migrar `dashboard/layout.tsx` a `sidebar-shell.tsx`.** Son paradigmas de interacción distintos a propósito (tab-bar + hoja "Más" en móvil vs. drawer lateral) y el intento de unificar el layout completo es un refactor de alcance mucho mayor al de esta fase, con riesgo de romper la campana de notificaciones, el avatar del header móvil y el propio tab-bar. En su lugar: **extraer sólo el renderizador del item-de-grupo** (la cabecera colapsable + lista de hijos) a un componente compartido nuevo, p. ej. `apps/web/components/nav-group.tsx`, que:
- lo importa `sidebar-shell.tsx` para su `<nav>` interno (afecta tenant-admin, admin —aunque admin no tiene grupos— y professor),
- lo importa `dashboard/sidebar-nav.tsx` para su lista de escritorio,

### 4. Drive URL validation

**Formas reales de una URL de carpeta de Google Drive** (confirmado por conocimiento de dominio + búsqueda; sin fecha de publicación específica de 2026 porque el formato es estable desde hace años):
- `https://drive.google.com/drive/folders/<ID>`
- `https://drive.google.com/drive/folders/<ID>?usp=sharing` / `?usp=drive_link`
- `https://drive.google.com/drive/u/<n>/folders/<ID>` (cuando el usuario tiene varias cuentas de Google logueadas, `n` es el índice de cuenta)
- `https://drive.google.com/open?id=<ID>` (formato antiguo, sigue funcionando, host sigue siendo `drive.google.com`)
- Carpetas de Unidad Compartida ("Shared Drive"): mismo shape `drive.google.com/drive/folders/<ID>`, a veces con `?resourcekey=<...>` añadido — mismo host.
- Un acceso directo ("shortcut") a una carpeta, al abrirse, resuelve a la misma URL de carpeta — no introduce un shape distinto.
- `docs.google.com` es normalmente para documentos/hojas/presentaciones individuales, no carpetas — pero CONTEXT lo incluye explícitamente en el allowlist como decisión ya tomada, así que se respeta tal cual (por si IBIZA structura su expediente con un índice en Google Docs en vez de una carpeta cruda).

**La ventaja de validar por host+esquema y no por regex de path**: todas las variantes de arriba comparten host (`drive.google.com`) y esquema (`https:`) sin compartir un shape de *path* único — una regex que intente capturar `/drive/folders/`, `/drive/u/\d+/folders/`, `/open` a la vez es frágil y quedará desactualizada en cuanto Google cambie un detalle de ruta. Validar `new URL(input).hostname` contra un `Set` cerrado es exactamente el mismo principio de seguridad que ya usa `sanitize-manual-html.ts` (allowlist cerrado de clases/esquemas) — la fase 3 ya estableció este patrón en el repo.

**No existe ningún helper de validación de URL reutilizable hoy** (grep de `new URL(`, `isValidUrl`, `validateUrl`, `ALLOWED_HOSTS` en todo `lib/` → cero resultados relevantes). Hay que construirlo desde cero:

```typescript
// apps/web/lib/drive-url.ts — puro, sin node:fs, importable desde cliente y servidor
const ALLOWED_DRIVE_HOSTS = new Set(["drive.google.com", "docs.google.com"]);

export function isValidDriveUrl(value: string): boolean {
  let url: URL;
  try {
    url = new URL(value);
  } catch {
    return false;
  }
  return url.protocol === "https:" && ALLOWED_DRIVE_HOSTS.has(url.hostname.toLowerCase());
}
```

**Hallazgo importante — el repo YA tiene un enlace externo pegado por un usuario y renderizado sin ninguna validación**, que sirve de advertencia de lo que NO hay que repetir: `AdvisorySession.meetingUrl` (`packages/db/prisma/schema.prisma:1294`) se escribe en `lib/actions/advisory.ts:173` (`let meetingUrl = (formData.get("meetingUrl") as string) || null;` — sin ninguna validación de formato) y se renderiza en `app/dashboard/advisory/page.tsx:131-135` como:
```tsx
{s.meetingUrl && (
  <a href={s.meetingUrl} target="_blank" rel="noopener noreferrer">
```
Esto es exactamente la forma en que hay que renderizar el enlace de Drive (mismo `target="_blank" rel="noopener noreferrer"`, es el único precedente de "enlace externo pegado por el usuario" en todo el repo), **pero sin repetir la ausencia de validación**. Es un hallazgo de seguridad pre-existente, fuera del alcance de esta fase arreglar, pero vale la pena señalarlo como antipatrón a no copiar.

**Redirect en servidor vs. `<a target="_blank">` directo — argumentado:** El único precedente real en el repo para "un usuario pega un enlace externo y otro usuario lo sigue" es la anchor directa de `meetingUrl` de arriba — no existe ningún patrón de "ruta de redirect" para enlaces externos en `app/api/*` (las rutas de `/api/upload/*` y `/files/*` sirven contenido propio autenticado, no redirigen a hosts externos). Construir una ruta de redirect nueva (`/api/drive-redirect?...` con `NextResponse.redirect()`) sería infraestructura sin precedente para un beneficio marginal: una ruta de redirect sólo revalida en el momento del clic, mientras que **validar en cada lectura del servidor** (en la query que arma la página, antes de decidir si renderizar el `<a>` o el mensaje "sin enlace configurado") revalida en *cada carga de página*, lo cual es una garantía más fuerte y no más cara. Recomendación: **`isValidDriveUrl()` se llama en la escritura (server action) Y en cada punto de lectura que vaya a exponer el enlace** (las queries que alimentan `CompanyProjectPanel`, `ManualOverviewPage`, `EvidenceBlock`, `EvidenceDetail`) — si la validación de lectura falla (fila corrupta, editada a mano, etc.), esos componentes muestran el mismo mensaje que "proyecto sin enlace" en vez de un `<a href>` con una URL no confiable. Esto satisface literalmente "no confiar sólo en la validación de escritura" sin inventar una pieza de infraestructura nueva.

## Don't Hand-Roll

| Problema | No construir | Usar en su lugar | Por qué |
|---|---|---|---|
| Validar que una URL es de Google Drive | Una regex de path que intente cubrir todos los shapes de Drive | `new URL(value)` nativo + `Set` de hosts permitidos + chequeo de `protocol === "https:"` | Los shapes de path de Drive cambian con el tiempo (`/drive/folders/`, `/drive/u/N/folders/`, `/open?id=`); el host no cambia. Es el mismo principio que ya usa `sanitize-manual-html.ts` con esquemas de enlace (`http`, `https`, `mailto`) |
| Persistir qué grupo del menú está abierto/cerrado | Un store de cliente nuevo (context, Zustand, `localStorage`) | Derivarlo de `pathname` en cada render con `useMemo`, más un `useState` local si se quiere permitir abrir manualmente otros grupos | El repo no tiene ningún store de cliente hoy; introducir uno para esto sería la primera instancia y un precedente pesado para un problema que ya resuelve el hecho de que el layout no se desmonta entre navegaciones |
| Distinguir "kind FILE con archivo en PROL" de "kind FILE con archivo en Drive" | Un nuevo valor de enum + lógica de bifurcación en cada capa | Reutilizar `FILE` — no hay coexistencia real que modelar (ver argumento completo arriba) | Ver sección de arquitectura §1 |

**Key insight:** esta fase no tiene un dominio de "problema deceptivamente complejo" que alguien ya resolvió en una librería (no es autenticación, no es parsing de fechas, no es sanitización de HTML). El riesgo aquí no es reinventar una rueda externa, es **sobre-construir infraestructura interna** que el repo no necesita todavía (un store de cliente, una ruta de redirect, un enum nuevo) para un problema que ya cabe en las convenciones existentes.

## Common Pitfalls

### Pitfall 1: `packages/db/prisma/schema.prisma` está siendo editado en vivo por otra sesión — confirmado, no hipotético

**Qué pasa:** al momento de esta investigación, `git status` en este mismo working tree muestra `packages/db/prisma/schema.prisma` modificado sin commitear, junto con otros 17 archivos de una segunda sesión interactiva de DC-3.

**Por qué importa:** cualquier tarea de esta fase que edite el schema debe re-verificar `git diff packages/db/prisma/schema.prisma` inmediatamente antes de tocarlo (el estado puede haber avanzado desde esta investigación), y usar ediciones puntuales y pequeñas — nunca `Write()` de un archivo completo, que sobrescribiría el trabajo ajeno.

**Verificado como no conflictivo hoy:** el diff actual de la otra sesión toca `Dc3CourseEdition`, `Dc3Certificate` y el bloque de relaciones de `Company` (aproximadamente líneas 1458-1680 del archivo). Los dos cambios que esta fase necesita —`Tenant.documentsMenuLabel` (cerca de la línea 507) y `ManualAssignment.driveUrl` (dentro del modelo en líneas 2643-2682)— caen en regiones completamente distintas del archivo. No hay solapamiento de líneas hoy, pero **esto es una fotografía de un archivo que se sigue moviendo**, no una garantía permanente.

**Cómo evitarlo:** editar con el tool de `Edit` (diff puntual), no `Write`; confirmar el `git diff` justo antes; si el plan se ejecuta en una ola distinta a cuando se investigó, repetir esta verificación.

### Pitfall 2: la etiqueta "Archivo que sube el cliente" queda falsa si no se actualiza

`KIND_LABEL.FILE` en `section-requirements-editor.tsx:29` dice literalmente "Archivo que sube el cliente" — si el guard de `evidence.ts` se relaja pero esta etiqueta no se toca, el administrador que da de alta un requisito nuevo verá una descripción que ya no es cierta. Pequeño pero real: es la única etiqueta de texto que queda estrictamente incorrecta si se omite.

### Pitfall 3: `/api/upload/evidence/route.ts` queda huérfana

Una vez que `evidence-block.tsx` deja de llamar a `/api/upload/evidence` para requisitos `FILE`, esa ruta (y el `subdir: "evidence"` de `storePrivateFile`) queda sin ningún llamador en la UI. No es necesario borrarla en esta fase (es código muerto inofensivo, y R2 mantiene el tier de plantillas activo de todos modos), pero **si alguien la borra, hay que confirmar primero que ningún otro flujo la usa** — confirmado por grep: es el único uso de `subdir: "evidence"` en todo el árbol de acciones de subida.

### Pitfall 4: no repetir el antipatrón de `meetingUrl`

`AdvisorySession.meetingUrl` se escribe y se renderiza sin ninguna validación de formato (ver sección de arquitectura §4). Es el único precedente de "URL externa pegada por un usuario" en el repo, y **no** es un patrón a copiar — esta fase es la primera vez que ese tipo de dato recibe una validación de host real, y debe quedar así, no seguir el ejemplo existente.

### Pitfall 5: lint baseline

La línea base es exactamente 81 avisos, 36 de ellos `@next/next/no-img-element`. Esta fase no necesita pintar ningún logo/imagen nueva — si el planificador decide mostrar el logo del tenant también en la cabecera del grupo de nav (no es necesario, ya está en `brand` por encima del nav), cualquier `<img>` nuevo necesita su `eslint-disable-next-line` con motivo para no romper el conteo.

## Open Questions
