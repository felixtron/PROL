## Qué pasó con `/api/upload/evidence`

**Retirada, con la prueba de cero llamantes.** Tras reescribir `evidence-block.tsx` en la tarea 2 (que era el único llamante conocido y confirmado), el grep de la tarea 3:

```
grep -rn "api/upload/evidence" apps/web packages | grep -v ".next" | grep -v ".turbo"
```

devolvió **cero resultados**. Se borró `apps/web/app/api/upload/evidence/route.ts` (y el directorio `evidence/` vacío bajo `api/upload/`). Con la ruta fuera, `submitEvidence` dejó de aceptar `input.file` en su firma: el `create` ahora escribe `fileKey: null, fileName: null, fileSize: null, mimeType: null` explícitamente, con un comentario explicando que las cuatro columnas se conservan en el esquema **para las filas históricas**, que se siguen descargando por `/files/evidence/:id`. Esto además cierra una vía de escritura que ya no tenía dueño: sin la ruta, `input.file` sólo sobrevivía como un RPC por el que un cliente autenticado podría haber intentado adjuntar a su propia evidencia una `fileKey` que no le pertenecía (nunca se demostró que esto fuera explotable — el `create` no validaba la propiedad de la `fileKey` recibida — pero quitar el parámetro cierra la pregunta de raíz).

`storePrivateFile`, `/api/upload/document-body`, `/api/upload/document-template` y `/files/*` no se tocaron: las plantillas confidenciales siguen en R2, que pierde el tier de evidencias y conserva el de plantillas.

## Hallazgo durante la limpieza: `deleteEvidenceRequirement` rehusó borrar

El plan preveía `deleteEvidenceRequirement(<id>)` como la vía de limpieza ("borra el requisito y arrastra sus actividades y sus evidencias de prueba"). En la ejecución real, la acción devolvió:

```json
{"success":false,"error":"Ya hay evidencias entregadas para este requisito. No se puede eliminar."}
```

Revisando el código (`lib/actions/manual.ts:758-766`), es una guarda **intencional**: `deleteEvidenceRequirement` cuenta `db.evidence.count({ where: { activity: { requirementId } } })` y rehúsa si hay alguna — protege el expediente de auditoría de un requisito real contra un borrado que se llevaría evidencias ya entregadas por debajo. **No es un bug de este plan ni del código existente**; es exactamente la clase de guarda que DRV-04 dice que PROL debe conservar. La limpieza del fixture que este plan fabricó se hizo con `DELETE` SQL directo (`evidence_reviews` → `evidences` → `compliance_activities` → `evidence_requirements`, en ese orden por las FK), mismo precedente que el script desechable de 03.1-03 para su tenant de prueba. `setProjectDriveUrl({assignmentId, driveUrl: null})` sí se ejecutó por HTTP real, sin necesidad de rodeo.
